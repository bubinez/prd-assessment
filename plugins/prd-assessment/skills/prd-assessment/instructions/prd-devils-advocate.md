# PRD Assessment — Step 12: Devil's Advocate Review

При выполнении Step 12 пайплайна /prd-assessment — следуй этой инструкции.

Шаг выполняется **агентом самостоятельно**: агент играет все роли, генерирует атаки и защиту. Пользователю выводятся **только нерешённые разногласия**.

## Input
PRD (`prd.md` после Step 11 Self-Review), `codebase-analysis.md`.

---

## Концепция

Step 11 проверяет PRD по **формальным** guard rails (формулировки, структура, чеклисты).
Step 12 проверяет PRD по **содержательным** критериям: полнота процессов, безопасность, UX, архитектурная целесообразность — через **ролевую симуляцию стейкхолдеров**.

Отдельный фокус этого шага: поймать ошибки, которые формальный чеклист не видит:
- перепутанный **main scenario** и fallback/edge case;
- незафиксированная **symmetry** у парных действий;
- неописанная **convergence** между локальным состоянием и внешней системой;
- **documentation drift** и отсутствие канонического runtime-документа.

---

## Роли

## Протокол вживания в роль

Этот шаг не считается выполненным, если агент просто пробежал чеклист общими словами.
Агент действует не как "защитник решения", а как "конструктивный оппонент".
Для каждой применимой роли агент обязан:
- сформулировать хотя бы одну **конкретную** атаку от лица этой роли, а не абстрактное «всё ли учтено?»;
- опираться на реальные FR / диаграммы / codebase findings;
- показать, почему роль либо нашла gap, либо была убедительно отбита;
- не подменять ролевой стресс-тест пересказом уже известных выводов.

Если роль нерелевантна для фичи, это нужно явно кратко зафиксировать, а не молча пропустить.

## Действия

### 1. Загрузить контекст

- Прочитать `prd.md` (Goals, FR, User Stories, Non-Goals, OQ, Risks).
- Прочитать `codebase-analysis.md`.
- Определить Feature Classification (из Step 1) для выбора применимых ролей.

---

### 2. Для каждой применимой атакующей роли — раунд атаки

Агент последовательно «надевает шляпу» каждой роли и генерирует **2–4 атакующих вопроса/утверждения**.

#### A1 — Вредный проджект (процессы и зависимости)

Из банка вопросов (выбрать применимые, не все):

1. Есть ли задача на получение доступов / ключей / credentials от внешней стороны?
2. Кто и когда проводит демо/приёмку с клиентом? Есть ли это в Change Plan?
3. Есть ли задача на runbook / документацию для поддержки?
4. Кто валидирует данные после миграции / первого запуска?
5. Учтён ли план отката (rollback), если фича сломает прод?
6. Code review, тестирование на staging — учтены в оценках или «бесплатно»?
7. Есть ли задача на мониторинг / алерты / healthcheck для нового функционала?
8. Кто отвечает за обновление API-документации?
9. Есть ли зависимость от действий клиента (предоставить данные, подтвердить формат)?
10. Что произойдёт, если этот проект заморозят на 3 месяца — нужен ли «консервационный» план?
11. *(для `integration`):* Проанализирована ли документация внешнего API в codebase-analysis.md (§ External Systems)? Все ли аспекты покрыты (rate limits, sandbox, SLA)? Нет ли пробелов, оформленных как OQ без дедлайна?
12. *(для `integration`):* Есть ли задача на настройку sandbox / тестовой среды внешнего сервиса? Кто запрашивает тестовые credentials?
13. *(для `integration` с external party):* Если часть реализации выполняет внешняя команда (клиент, партнёр) — заложено ли время нашей команды на **поддержку** в период их разработки? (ответы на вопросы, review PR, совместные тесты, bug-fix по их отзывам). Если нет — это **систематическое занижение оценки**: разработчик де-факто тратит это время, но оно нигде не учтено.
14. *(для `integration`, `architecture`):* Есть ли в PRD диаграмма потока данных? Без неё невозможно составить Change Plan — неизвестно, какие handoff-ы между системами нужно планировать.
15. *(для фич с runtime docs):* После реализации останется один канонический документ или команда получит ещё один слой противоречащих описаний? Где это зафиксировано в PRD и Change Plan?

#### A2 — Скептичный архитектор (избыточность)

1. Проверены ли ВСЕ существующие модули — нет ли аналога в кодовой базе?
2. Нет ли feature-flag или конфигурации, которая включит нужный функционал без нового кода?
3. Можно ли решить задачу расширением конфига / параметризацией вместо нового модуля?
4. Есть ли в другом проекте компании готовое решение, которое можно переиспользовать?
5. Что если не делать эту фичу вообще — каков реальный бизнес-ущерб в цифрах?
6. Нет ли в codebase-analysis.md упоминания модулей, которые покрывают 80%+ требуемого?
7. Можно ли заменить custom-реализацию на SaaS / managed service?
8. *(для `integration`):* Не заложена ли избыточно сложная схема взаимодействия (авторизация, протокол, маппинг), если внешняя система поддерживает более простой вариант? Проверь: может, вместо OAuth2 + custom webhook достаточно статичного API key; вместо двусторонней синхронизации — одностороннего push; вместо значительных доработок на стороне внешней системы — готового механизма, который она уже предоставляет. *(Пример: «Не верю, что нужна такая сложная авторизация через значительные доработки на стороне CRM. Поищи более простое решение.»)*
9. *(для `integration`, `architecture`):* Component diagram в PRD — участники диаграммы совпадают с реальными сервисами из codebase-analysis.md? Или там абстракции вроде «Backend», «Frontend», «CRM» без указания конкретных модулей и протоколов?

#### A3 — Параноидальный безопасник (security & compliance)

1. Где хранятся секреты (токены, ключи) и кто имеет к ним доступ? Есть ли vault/rotation?
2. Новые endpoints — есть ли rate-limiting и authentication?
3. Логи операций — не содержат ли PII (email, телефон, ИНН)?
4. Webhook / incoming API — есть ли валидация подписи (HMAC, JWT)?
5. Данные в transit — TLS обязателен? А at-rest encryption?
6. Есть ли аудит действий администратора / привилегированных операций?
7. Что если злоумышленник подменит payload во входящем вызове?

#### A4 — Капризный пользователь (UX edge cases)

1. Что видит пользователь при пустом состоянии (0 записей, первый вход)?
2. Сколько кликов / шагов до целевого действия? Можно ли сократить?
3. На медленном интернете — будет ли индикатор загрузки или интерфейс «зависнет»?
4. Есть ли undo / отмена для деструктивных действий?
5. Что если пользователь закроет вкладку посреди многошаговой операции?
6. Адаптивность: работает ли на мобильном / планшете (если применимо)?
7. Сообщения об ошибках — понятны ли обычному пользователю, а не разработчику?
8. Не назван ли основной пользовательский сценарий `fallback` только потому, что он технически сложнее? Если пользователь чаще всего идёт по нему, это должен быть main scenario в PRD.

#### A5 — QA-перфекционист (системные corner cases)

Проверяет, что FR **содержательно** покрывают edge cases, а не просто «галочка стоит» после Step 11 Self-Review. Для каждой применимой категории из Step 1 (§6b) берёт конкретный FR и задаёт вопрос «а что если...».

1. **Race condition:** FR описывает создание/обновление записи — а что если два запроса придут одновременно? Есть ли в FR упоминание блокировки, upsert, или optimistic locking? Или FR написан только для «один пользователь, один запрос»?
2. **Частичный сбой:** FR описывает цепочку действий (создать запись + отправить webhook + обновить кэш) — а что если шаг 2 упал? Система в консистентном состоянии? FR-err описывает именно этот сценарий, или только «при ошибке вернуть 500»?
3. **Идемпотентность:** FR описывает входящий API — а что если тот же запрос придёт дважды (retry от клиента, дубль от webhook)? Будет дубликат записи или idempotency key?
4. **Большой объём:** FR описывает список/выборку — а что если записей 10 000? Есть ли pagination в FR? А если фильтр вернёт 0 записей — что происходит?
5. **Устаревшие данные:** FR использует кэш или читает данные — а что если данные изменились между чтением и действием? TTL кэша определён? Инвалидация описана?
6. **Таймауты:** FR вызывает внешний сервис — а таймаут указан? Что если внешний сервис отвечает 30 секунд вместо 2? Пользователь/система ждёт или есть circuit breaker?
7. **Граничные значения данных:** FR принимает входные данные — а что если строка пустая, число = 0, дата в прошлом, спецсимволы в имени, Unicode, emoji? Валидация описана или подразумевается?
8. **Порядок операций:** FR описывает несколько связанных действий — а что если порядок нарушен (webhook пришёл раньше, чем запись создана; уведомление отправлено до подтверждения)?
9. **Request path trace (для `integration`, `architecture` с новым доменом/proxy):** возьми конкретный User Story и пройди полный путь запроса от браузера/клиента до ответа: каждый hop (DNS → proxy → сервис → БД), домен, протокол, кто обрабатывает. Для каждого типа ресурса отдельно: HTML-страница, JS/CSS, API-вызов. Есть ли хоп, который Feature не затронула, но должна была — остался на старом домене/сервере?
10. **Static vs dynamic split (для `integration`, `architecture` с новым доменом):** явно перечисли что отдаётся с нового домена/proxy, а что остаётся на основном сервере. Нет ли ссылок в HTML/JS/CSS которые hardcode'ят старый домен или генерируются Django `{% static %}` без учёта нового routing'а?
11. **Implicit call contract (если в codebase-analysis.md есть секция `## Implicit Call Contracts`):** для каждого контракта из таблицы — FR описывает ожидаемый **side-effect** явно (какая DB-запись создаётся, какое поле обновляется, какой сигнал срабатывает)? Или только «высокоуровневый» исход, допускающий реализацию без обязательного вызова? Типичные паттерны провала и критерии оценки — см. `rules/implicit-call-contracts.md в каталоге скилла`.
12. **Symmetry check:** если в фиче есть парные действия, действительно ли они симметричны по payload, auth, response, side-effects, tests и docs? Если асимметрия намеренная — это явно записано в PRD? Если нет — это gap.
13. **Convergence check:** если локальный статус синхронизируется с внешней системой, описано ли, какая система является source of truth и как достигается автоматическая конвергенция после временного сбоя?

> **Методика:** не задавать абстрактно «а corner cases покрыты?». Взять конкретный FR (например FR-3) и конкретный сценарий (например «два CRM одновременно создают клиента с одним email») — и проверить, есть ли в FR явный ответ.

#### A6 — Архитектор-визуал (диаграммы как инструмент проверки решения)

Применяется для `integration`, `backend` (с внешними зависимостями), `architecture`.  
Роль: архитектор, который **не может дать техническую оценку PRD без визуализации** — текст FR для него недостаточен.

1. **Sequence diagram отсутствует или неполна:** «Я не вижу sequence diagram. FR-X описывает поток [A→B→C], но я не понимаю: кто инициирует вызов, в каком порядке, что происходит при таймауте шага 2. Без диаграммы я не могу подтвердить, что архитектура корректна.»
2. **Component diagram не показывает реальные модули:** «Component diagram есть, но участники — абстракции. Покажи реальные сервисы из codebase-analysis.md с протоколами на стрелках. Иначе непонятно, какие модули затрагивает изменение.»
3. **Error path не визуализирован:** «В sequence diagram показан только happy path. Где ветка с ошибкой? FR-X-err описывает поведение при сбое, но я не вижу, как это выглядит в потоке данных.»
4. **Field mapping отсутствует:** *(только если ≥5 полей маппируются между системами)* «FR описывает маппинг [N] полей, но я не вижу таблицы маппинга. Без неё непонятно, где трансформация, где прямое копирование, и где могут быть конфликты типов.»
5. **Синтаксис Mermaid сломан:** «Диаграммы есть, но они не рендерятся — вижу синтаксическую ошибку. Сломанная диаграмма хуже отсутствующей: создаёт иллюзию визуализации, а фактически нечитаема.» Проверить каждую диаграмму:
   - `sequenceDiagram`: нет HTML-тегов (`<br/>`, `<...>`) в именах участников и подписях стрелок; все `alt/else/end` сбалансированы; подписи однострочные или вынесены в `Note over`
   - `graph LR/TD`: нет `<br/>` в node labels; спецсимволы (`/`, `(`, `)`, `-`) в label — в кавычках; все `subgraph` закрыты `end`; нет зарезервированных слов без кавычек (`end`, `graph`, `note`, `loop`)
   - Вердикт при синтаксической ошибке — всегда **ACCEPTED**: агент исправляет через Edit/StrReplace/replace_file_content.
6. **Markdown rendering сломан вне диаграмм:** «Я вижу текст, который рендерится не так, как задумано — зачёркивание там, где должно быть число, курсив там, где должна быть переменная. PRD теряет читаемость.» Проверить весь текст PRD:
   - **Одиночные тильды** как «приблизительно»: `~50%`, `~6 дней`, `~0.6 спринта` — если в строке ≥2 одиночных `~`, рендерер может показать зачёркивание. Заменить на `≈`.
   - **Незакрытые `*` или `_`** внутри слов — могут формировать случайный курсив/жирный.
   - **Незакрытые обратные кавычки** — весь последующий текст попадает в code span.
   - Вердикт при нарушении — всегда **ACCEPTED**: агент заменяет через Edit/StrReplace/replace_file_content по конкретному месту.

#### A8 — DBA / Архитектор данных (схема БД и миграции)

Применяется для `backend`, `integration`, `architecture`. Пропускать для `UI-only`.
Роль: DBA, который читает раздел **Database Changes** и не может одобрить решение, не убедившись в полноте и корректности изменений схемы.

1. **Раздел отсутствует или пустой:** «Database Changes не заполнен. Я не знаю, что именно меняется в схеме. FR-X явно подразумевает новую таблицу/поле — почему её нет в разделе? Без этой информации я не могу оценить ни сложность миграции, ни риск простоя.»
2. **Нет стратегии миграции:** «Описаны новые поля/таблицы, но нет слова о миграции. Это zero-downtime migration? Нужен ли backfill существующих строк? Если таблица большая — время блокировки критично. Без ответа на этот вопрос задача CP-X.Y занижена минимум вдвое.»
3. **Backfill через Python ORM на большой таблице:** «FR описывает backfill существующих данных. Если в таблице >50k строк — Python ORM (итерация + bulk_create) в разы медленнее, чем `INSERT INTO ... SELECT` на стороне БД. Указан ли в Database Changes метод backfill? Если нет — реализация по умолчанию выберет ORM-итерацию, что на 1M+ строках займёт минуты вместо секунд.»
4. **Триггеры активны во время массового UPDATE/INSERT:** «Если миграция создаёт триггер, а затем делает bulk UPDATE или backfill — триггер срабатывает на каждую строку. На 1M строк это превращает один UPDATE в 1M дополнительных write-операций. Зафиксирован ли в Database Changes правильный порядок: массовые операции ПЕРЕД созданием триггеров?»
3. **Отсутствуют индексы:** «FR-X описывает выборку по [полю] с фильтрацией/сортировкой, но в Database Changes нет упоминания индекса на это поле. На таблице с 10 000+ строк это будет full scan. Добавлен ли индекс намеренно отсутствует или просто забыт?»
4. **Риск целостности данных:** «Удаляется поле / таблица, на которую могут ссылаться другие модели. Есть ли CASCADE / SET NULL / RESTRICT в Database Changes? Или миграция просто дропает колонку и рассчитывает, что всё само рассыплется в prod?»
5. **Rollback схемы:** «Change Plan содержит задачу на миграцию, но нет задачи на rollback схемы. Если деплой упадёт после apply migration — как откатить? Описан ли down-migration?»
6. **Явное «нет изменений» не обосновано:** «Database Changes содержит "No database changes required", но FR-X явно описывает сохранение нового типа данных / нового состояния. Это противоречие. Либо FR неверен, либо раздел не заполнен.»
7. **Инвариант таблицы не верифицирован через тест:** «FR-X вводит инвариант для таблицы [название] — например, "не создавать записи для is_deleted=True" или "только активные источники". Но в Testing Strategy нет верификационного теста, который проверяет этот инвариант глобально после выполнения всех операций фичи (SELECT COUNT(*) ... WHERE нарушение = 0). Без такого теста инвариант покрыт только для сценария, который автор имел в виду — другие пути записи в эту таблицу останутся непроверенными.» Применяется только если PRD содержит FR с явным инвариантом данных (фильтр включения/исключения, запрет на определённые записи).

> **Методика:** для каждой атаки сверяться с конкретными FR, которые подразумевают изменения данных (создание/обновление/удаление сущностей, новые статусы, новые связи).

#### A9 — Противник техдолга (архитектурные неэффективности из Step 4)

Применяется для `backend`, `architecture` **только если** в `codebase-analysis.md` есть секция `## Architectural Findings` с хотя бы одной записью.
Роль: старший разработчик, который читал `codebase-analysis.md` и проверяет, что команда не «проглотила» найденные проблемы молча.

1. **Решение не зафиксировано:** «В codebase-analysis.md обнаружена архитектурная неэффективность: [название из Architectural Findings]. Я не вижу в PRD ни FR на исправление, ни записи в Risk Register (техдолг), ни обоснования "оставить как есть". Это значит, проблема проигнорирована. Это недопустимо — без явного решения она будет воспроизведена в новом коде.»
2. **Костыль вместо исправления:** «Finding [название] предлагает [правильное решение из Architectural Findings], но в PRD я вижу [описание того, что реально написано] — это workaround, а не решение. Разница: workaround маскирует симптом, решение устраняет причину. Если scope не позволяет исправить сейчас — зафиксируй как техдолг с конкретным assessment-ом, а не латай.»
3. **Решение пользователя не отражено в PRD:** «Пользователь выбрал вариант [a/b/c] в Scope Checkpoint Step 4. Вариант [a] — исправить архитектурно — не реализован в FR. Вариант [b] — зафиксировать как техдолг — не отражён в Risk Register. Вариант [c] — обоснование оставить как есть — не записано.»

> **Методика:** для каждой записи в `## Architectural Findings` из `codebase-analysis.md` — искать соответствующий след в prd.md (FR, Risk Register запись с пометкой «Техдолг», или явное обоснование). Если след не найден → атака.

> **Вердикты:**
> - Если найден FR на исправление или Risk Register запись → DEFENDED.
> - Если след отсутствует и проблема реальная → ESCALATE (пользователь должен явно выбрать a/b/c).
> - Если предложен workaround вместо решения → ESCALATE.
> - ACCEPTED не используется для этой роли: решение о scope фичи принимает пользователь, не агент.

#### A10 — QA Lead / Test Strategy Reviewer (тесты и документация)

Применяется **всегда**.
Роль: QA Lead, который читает раздел **Testing & Documentation Strategy** и проверяет полноту test coverage, актуальность документации и наличие тестов для критических путей.

1. **Раздел отсутствует или пустой:** «Testing & Documentation Strategy не заполнен. Я не знаю, какие тесты нужны. FR-X явно подразумевает критический путь — почему нет Unit Tests для неё? Без test strategy я не могу оценить риск регрессии и качество кода.»
2. **Unit Tests — отсутствуют для критических путей:** «FR-X описывает [критический процесс], но в Testing & Documentation Strategy нет упоминания Unit Tests для этого модуля. Это critical path — он требует ≥3 тестов (happy path, ошибка, edge case). Почему их нет?»
3. **Integration Tests не спланированы:** «FR-Y описывает взаимодействие между [компонент A] и [компонент B], но нет Integration Tests в strategy. На интеграции часто всплывают баги, которые Unit Tests не ловят. Где план по integration тестированию?»
4. **Edge cases не покрыты тестами:** «FR-X описывает обработку [большой объём / пустой входные данные / таймаут], но Testing Strategy не упоминает тесты для этих edge cases. Если не тестировать — это риск регрессии в prod.»
5. **Документация не актуализирована:** «Фича меняет [API / User Experience / Database schema / Config], но Documentation Updates в strategy не содержит пункта на обновление [API docs / User Guide / Admin Guide / Migration Guide]. Кто будет обновлять docs? Когда?»
6. **Невозможно онбордить нового разработчика:** «Я новый разработчик и получил эту фичу. Нет docs на то, как развернуть фичу локально, как запустить тесты, как проверить, что всё работает. Это замедляет онбординг на дни. Где runbook / setup guide?»
7. **Docs drift:** «PRD меняет runtime-контракт, но я не вижу, какой документ станет каноническим после реализации и кто почистит старые противоречащие описания. Это почти гарантированный источник путаницы после релиза.»

> **Методика:** для каждого FR проверить, есть ли соответствующий пункт в Unit/Integration Tests. Для каждого изменения системной документации (API, schema, flows) проверить, есть ли пункт в Documentation Updates.

> **Вердикты:**
> - Если strategy полна и покрывает все FR → DEFENDED.
> - Если стратегия есть, но неполна (забыты edge cases, не обновлена docs) → ACCEPTED (агент добавляет недостающие пункты).
> - Если strategy отсутствует или полностью пустая → ESCALATE (пользователь должен явно спланировать тесты и docs).

#### A7 — Новый член команды (понятность PRD с нуля)

Применяется для `integration`, `architecture`.
Роль: разработчик, который **впервые читает этот PRD** и пытается понять, что происходит — только по тексту, без контекста команды.

1. **Нет общей картины:** «Я прочитал PRD и не понимаю, как системы связаны. Есть FR с деталями, но нет ни одного визуального обзора. Если бы была диаграмма компонентов — я бы за 30 секунд понял архитектуру, а не читал 20 FR подряд.»
2. **Поток данных непонятен из текста:** «FR-3 описывает синхронизацию, FR-7 — обработку ошибок, FR-12 — retry. Но я не могу из этих FR собрать цельную картину: что за чем идёт. Sequence diagram решила бы это немедленно.»
3. **Онбординг нового разработчика:** «Если завтра в команду выйдет джун и получит этот PRD — сколько вопросов у него возникнет? Диаграммы — это не украшение, это экономия времени на онбординг и ревью.»

#### A11 — Deployment Engineer (артефакты и их доставка)

Применяется для `integration`, `architecture`.
Роль: инженер по деплою, который читает PRD и проверяет, что **каждый артефакт** (HTML, JS/CSS, бинарник, конфиг, секрет) явно приписан к серверу/домену и способу доставки. Не допускает ситуации «появится само».

1. **Артефакт-матрица неполна:** «Я вижу в PRD новый сервер/домен, но не вижу явного списка: что именно на нём живёт, как туда попадает при деплое и кто владелец обновления. Для каждого типа файла/сервиса должен быть ответ: где в prod, как доставляется (docker pull / rsync / git clone), при каком событии обновляется.»
2. **Статика vs динамика не разграничена:** «PRD вводит новый proxy-домен. Для Web App есть как минимум два типа ресурсов: HTML (рендерится сервером) и статика (JS/CSS/images). Явно ли описано что отдаётся напрямую с proxy-диска, а что проксируется на основной сервер? Без этого разграничения реализация угадывает.»
3. **Порядок деплоя не зафиксирован:** «Если A зависит от B (proxy нужен до смены setWebhook URL, статика должна быть на диске до открытия Web App) — отражён ли этот порядок явно в Change Plan через `Depends`? Или задачи можно выполнять в произвольном порядке?»
4. **Rollback per artifact:** «Change Plan содержит rollback для сервиса, но что происходит с каждым артефактом при откате отдельно? Можно ли откатить только статику без отката Go-бинарника? Если нет — это жёсткая связь, которая нигде не зафиксирована.»

> **Вердикты:**
> - Матрица есть, порядок зафиксирован → DEFENDED.
> - Разграничение статики/динамики отсутствует или порядок деплоя не через `Depends` → ACCEPTED (агент добавляет таблицу или `Depends` в Change Plan).
> - Артефакт без явного способа доставки → ESCALATE (пользователь выбирает: rsync / docker volume / git submodule / другое).

---

### 3. Защита — Защитник PRD (Lead)

После генерации всех атак агент «надевает шляпу» Защитника и для **каждой атаки** пытается дать обоснованный ответ:

- Ссылается на конкретный FR, Goal, Risk, Non-Goal, OQ из prd.md.
- Если атака покрыта существующим требованием — цитирует его: «Покрыто: FR-X описывает [поведение].»
- Если атака нерелевантна для данной фичи — объясняет почему: «Не применимо: фича не работает с PII / не имеет UI / etc.»
- Если атака валидна, но приоритет низкий — рекомендует OQ или Non-Goal вместо нового FR.

---

### 4. Классификация результатов

Каждую пару «атака — защита» классифицировать:

| Вердикт | Значение | Действие |
|---------|----------|----------|
| **DEFENDED** | Защитник убедительно ответил со ссылкой на PRD | Нет действий |
| **ACCEPTED** | Атака валидна, защита слабая, можно исправить автоматически | Агент вносит правку в prd.md (Edit/StrReplace/replace_file_content) |
| **ESCALATE** | Атака валидна, но нужно решение пользователя | Выводится пользователю с вариантами a/b/c |

---

### 5. Автоматические правки (ACCEPTED)

Для вердикта ACCEPTED агент вносит изменения в prd.md:
- Добавить недостающий FR / FR-err.
- Добавить Risk в Risks & Mitigations.
- Добавить OQ с владельцем и дедлайном.
- Добавить Non-Goal (если атака валидна, но out of scope).
- Выполнить обязательный follow-up внутри текущего scope без формулировок «если хотите, могу ещё проверить ...».

**Лимит:** не более 5 автоправок за шаг. Если больше — остальные → ESCALATE.

### 5a. Freeze Refresh / Rewind Rule

Если ACCEPTED-правка или ESCALATE-ответ пользователя меняет хотя бы одно из следующего:
- main scenario;
- component boundaries;
- shared task / queue / worker topology;
- source of truth / convergence;
- canonical docs topology;
- deployment artifact ownership;
- execution surface coverage;

то шаг **не может** считаться простым "локальным патчем".

В этом случае subagent обязан вернуть флаг:
- `freeze_refresh_required` — нужно обновить Step 10 и затем повторить Step 11;
- `rewind_required` — если найден новый adjacent path / mixed-use surface / execution surface gap, нужно вернуться в Step 5.
- `decision_required` — если атака выявила реальную развилку scope / boundaries / sibling-feature inclusion, которую нельзя честно закрыть без выбора пользователя.

При `decision_required` subagent обязан вернуть `questions_for_user`:
- `observed`
- `why_it_matters`
- `question`
- `options`

Запрещено тихо выбирать include/exclude для sibling feature того же класса, если это меняет PRD freeze.

### 7. Переход

## Guard Rails

- **Поиск в кодовой базе перед ESCALATE:** если атака касается технического факта о модели, поле, статусе, константе или поведении существующего кода — агент **обязан** найти ответ в кодовой базе (Grep/Read по `models/`, `services/`, `migrations/`) или документации (`Doc/`) перед тем, как выставить ESCALATE. Задавать пользователю вопросы о том, что можно проверить самостоятельно — запрещено.
- Агент НЕ добавляет атаки ради количества. Каждая атака должна быть **специфичной** для данной фичи.
- Если Feature Classification = `UI-only` — пропустить A3 (безопасник), A6 (визуал), A7 (новичок), A8 (DBA); сократить A1 до 2 вопросов.
- Если Feature Classification = `architecture` — пропустить A4 (пользователь), усилить A2 (архитектор) и A6 (визуал).
- Если Feature Classification = `backend` без внешних зависимостей — пропустить A6 и A7.
- Отсутствие ролевой конкретики = дефект выполнения шага. Формулировки «в целом ок», «похоже покрыто», «вероятно учтено» без ссылки на конкретные FR / артефакты запрещены.
- **A8:** применяется для `backend`, `integration`, `architecture`. Если раздел Database Changes содержит «No database changes required» — роль проверяет обоснованность этого утверждения (атака 6), затем пропускает остальные пункты при DEFENDED.
- **A9:** применяется только если в `codebase-analysis.md` существует секция `## Architectural Findings` с хотя бы одной записью. Если секции нет — роль пропускается без упоминания. ACCEPTED для A9 не используется: любое нерешённое finding → ESCALATE, решение принимает пользователь. Для каждого finding проверяется наличие следа в prd.md — FR, Risk Register (техдолг), или явное обоснование из Scope Checkpoint.
- **A10:** применяется **всегда**. Если раздел Testing & Documentation Strategy отсутствует → ESCALATE (нужна полная стратегия). Если стратегия есть, но неполна (edge cases без тестов, docs не обновлены) → ACCEPTED (агент добавляет недостающие пункты). Максимум 2–3 ACCEPTED автоправки от A10 за шаг; остальное → ESCALATE.
- Для применимых фич хотя бы одна атака должна явно проверить каждую из осей: **symmetry**, **convergence**, **docs drift**, **main scenario misclassification**. Если ось неприменима — это нужно кратко зафиксировать в DEFENDED.
- Максимум атак на роль: 4. Максимум ESCALATE на весь шаг: 5.
- Банк вопросов — отправная точка; агент адаптирует формулировки под контекст конкретной фичи.
- **A6 и A7:** если диаграммы уже есть в PRD и корректны — роли отмечают DEFENDED сразу, без лишних атак. Цель ролей — не требовать диаграммы «для галочки», а проверить их **наличие, содержательность и синтаксическую корректность**.
- **A6, атака 5 (синтаксис Mermaid):** выполняется всегда при наличии Mermaid-блоков, независимо от DEFENDED по атакам 1–4. Синтаксическая ошибка → ACCEPTED (автоправка). Если диаграммы синтаксически чисты → DEFENDED.
- **A6, атака 6 (Markdown rendering):** выполняется всегда для всего текста PRD, независимо от DEFENDED по атакам 1–5. Проверить весь документ на одиночные тильды `~` перед числами (≥2 в одной строке → потенциальное зачёркивание), незакрытые `*`/`_`, незакрытые кавычки. Нарушение → ACCEPTED (заменить `~` на `≈` через Edit/StrReplace/replace_file_content). Если документ чист → DEFENDED.
