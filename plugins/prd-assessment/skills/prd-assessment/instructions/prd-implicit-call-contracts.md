# Step 4 (5b): Implicit Call Contract Audit

**Цель:** Выявить паттерны в кодовой базе, где определённый вызов обязателен по соглашению, но **не защищён интерфейсом** (тип, декоратор, базовый класс не enforce-ят его). Задокументировать контракт явно, чтобы реализация и ревью могли опираться на него.

**Применяется когда:**
- Feature добавляет новый компонент (задача, сервис, метод) в конвейер, где уже действует implicit call contract
- PRD содержит фразы «по образцу существующих задач», «аналогично другим классификаторам», «переиспользовать паттерн» — сигнал, что паттерн есть, но нигде не задокументирован
- Feature меняет ветки выполнения существующего компонента, у которого есть обязательные side-effect вызовы

---

## Что такое Implicit Call Contract

Implicit Call Contract — это соглашение о том, что при определённом условии **конкретный вызов должен быть сделан явно**, и нарушение этого соглашения не обнаруживается статическим анализом или типами, а только в рантайме или через интеграционный тест.

**Примеры паттернов:**

| Паттерн | Обязательный вызов | Что теряется при пропуске |
|---------|-------------------|--------------------------|
| Celery конвейер с финализацией | `finalize_classification(id, result)` до `return` | DB-записи не создаются, статус не обновляется |
| Django ORM — изменение записи | `.save()` вместо `.objects.update()` | `post_save` сигналы не срабатывают |
| Django транзакция | явный выход из `atomic()` или `commit()` | данные не сохранены при исключении |
| Notification pipeline | `send_notification()` в success-ветке | пользователь не получает уведомление |
| Аудит / traceback | `update_classification_traceback()` в каждой ветке | трассировка пропадает для конкретного пути |
| Cache invalidation | `cache.delete(key)` после записи в БД | кэш устарел, клиент читает старые данные |

**Ключевой признак провала:** разработчик пишет логически корректный код (`return result_dict` с правильным статусом), все unit-тесты на return value проходят, но DB side-effect отсутствует — потому что явный вызов забыт.

## Процесс

### 1. Найти действующие implicit contracts в кодовой базе

Grep по существующим реализациям паттерна:
- Найти все аналоги нового компонента (например, другие Celery-задачи в конвейере)
- Для каждого — прочитать тело функции и выписать: какие вызовы делаются до `return` в каждой ветке?
- Задать вопрос: «если убрать этот вызов — что сломается молча?»

### 2. Для каждого выявленного контракта составить таблицу

```
| Ветка выполнения | Условие | Обязательный вызов | Вызов должен быть? | Ожидаемый side-effect |
|-----------------|---------|-------------------|--------------------|-----------------------|
| финальный статус | confidence >= threshold | finalize_classification(id, result) | ✅ явно до return | VacancyClassifier создан, status обновлён |
| передача дальше  | confidence < threshold  | apply_async только | ❌ finalize не нужен | — |
| ошибка модели    | MLModelNotAvailableError | apply_async только | ❌ finalize не нужен | — |
```

### 3. Сверить с FR в PRD

Для каждой ветки с обязательным вызовом — найти соответствующий FR и проверить:
- AC описывает конкретный **side-effect** (какая DB-запись создаётся, какое поле обновляется)?
- Или AC описывает только «высокоуровневый» исход («задача финализирует вакансию»), допускающий реализацию без явного вызова?

Если AC недостаточно конкретен — добавить/уточнить FR: «`X()` вызывается явно до `return`; в БД создаётся [запись]; [поле] принимает значение [Y]».

### 4. Зафиксировать в codebase-analysis.md

Добавить секцию `## Implicit Call Contracts` с таблицей из п.2 и описанием каждого паттерна:

```markdown
## Implicit Call Contracts

### [Название паттерна]

**Контракт:** [что должно быть вызвано, при каком условии]
**Нарушение:** [что теряется при пропуске]
**Существующие реализации:** [файлы, функции — для сверки]

| Ветка | Условие | Обязательный вызов | Нужен? | Side-effect |
|-------|---------|--------------------|--------|-------------|
| ...   | ...     | ...                | ✅/❌  | ...         |
```
