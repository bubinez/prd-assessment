# PRD Assessment — Step 1: Business Clarification

При выполнении Step 1 пайплайна /prd-assessment — следуй этой инструкции.

## Intellectual Opponent

Не принимать выводы пользователя за истину. Анализировать аргументы, искать противоречия. Варианты a/b/c с обоснованием. Объективность выше согласия.

---

## Действия

### 0. Resume Check (выполнять первым)

Если активирован **Resume Mode** (флаг `--resume` или авто-детект существующего `prd.md`):

1. **Прочитать** существующий `prd.md` — извлечь Goals, User Stories, OQ, MBQ-ответы (если сохранены).
2. **Вывести сводку** существующих бизнес-решений:

```
## Resume — Step 1: Business Clarification

Текущий PRD содержит:
- Goals: <резюме>
- MBQ: <статус ответов 1–4 или «не зафиксированы»>
- Open Questions: <список или «нет»>

Что изменилось с момента последнего assessment?
  a) Ничего — переподтвердить без изменений
  b) Изменились бизнес-цели / scope
  c) Изменились технические ограничения
  d) Нужно переоткрыть конкретные вопросы (укажите номера)
  e) Пройти весь Step 1 заново с нуля
```

3. Действовать по ответу:
   - **a** → зафиксировать контекст и перейти к следующему шагу без вопросов.
   - **b/c** → задать только вопросы, относящиеся к изменённой области (не повторять уже закрытые MBQ).
   - **d** → показать только указанные вопросы, подставив прежние варианты ответов как дефолт.
   - **e** → выполнить полный Step 1 как при новом ассессменте (игнорировать существующие ответы).

> При resume **не задавать** MBQ повторно, если они уже закрыты и пользователь выбрал a, b или c — только добавлять/корректировать.

---

### 1. Input Check
- **No input:** Промпт: «Опишите фичу, которую нужно оценить, или прикрепите файл с черновиком ТЗ (@file.md). Пример: /prd-assessment Добавить экспорт дашборда в PDF»
- Не продолжать без ввода.
- **Resume исключение:** при Resume Mode шаг 0 заменяет Input Check — input не нужен.

### 1b. Feature Classification (первым делом, до всех остальных вопросов)

Задать **один** вопрос — тип фичи. От ответа зависят лимиты шагов Step 4 и Step 9.

**FC-1. Тип фичи:**
- a) `UI-only` — изменения только во фронтенде/интерфейсе, без новой бизнес-логики
- b) `backend` — новая логика, API, DB-схема; фронтенд может затрагиваться
- c) `integration` — взаимодействие с внешней системой (API стороннего сервиса, webhook, синхронизация)
- d) `architecture` — рефакторинг, миграция данных, изменение инфраструктуры

**Последствия выбора:**

| Тип | Глубина Step 4 | Лимит техвопросов | Обязательные риски |
|-----|---------------|-------------------|--------------------|
| `UI-only` | Минимальная (только entry points + компоненты) | ≤3 | — |
| `backend` | Стандартная | ≤7 | Data quality |
| `integration` | Полная + внешние зависимости + **External System Analysis** | ≤10 | Delivery, Third-party, Data quality, Security |
| `architecture` | Полная + migration constraints | ≤10 | Backward compat, Migration rollback |

> Если тип неоднозначен — выбрать более сложный из двух кандидатов.

---

### 2. Parse
- Extract: entities, goals, scope hints.
- Если прикреплён файл — прочитай и извлеки описание.

### 3. Search First
- Для каждого потенциального вопроса ищи ответ в `docs/`, `ai_docs/`, в кодовой базе.
- **Unanswered only:** показывай пользователю только вопросы без найденного ответа.

### 4. Completeness Block
Перед вопросами выведи:

```
## Completeness — Step 1: Business Clarification

| Dimension | Current | Target | Gap |
|-----------|---------|--------|-----|
| Requirements clarity | X% | 100% | [что осталось] |

**Осталось:** [1–2 предложения для пользователя]

---
```

Оценка текущего % по шкале:
- 0% — No input
- 25% — Raw text
- 50% — Key entities
- 75% — No critical unknowns
- 100% — All closed

### 5. Вопросы
- **Пачкой до 10** вопросов за раз.
- У каждого — варианты (a, b, c) с кратким обоснованием «лучший вариант».
- **Формат ответа:** Nx (например 2a — вариант a вопроса 2).
- **If «0»:** пользователь не понял — объясни вопрос и варианты подробнее.
- **Rank:** от более важных к менее важным.
- **Language:** простые формулировки, как для стажера.

### 6. Mandatory Business Questions (always ask, before other topics)

Эти вопросы задавать **всегда** независимо от полноты ввода:

**MBQ-1. Статус сделки:**
- a) Контракт/NDA подписан — можно планировать разработку
- b) В процессе согласования — оценка нужна для КП
- c) Потенциальный лид, контракта нет

> ⚠️ Если ответ **c)** — вывести: «Разработка под неподтверждённый контракт несёт риск потери инвестиций. Рекомендуется: зафиксировать POC-бюджет, сделать минимальную оценку для КП, либо дождаться подписания перед планированием полного Change Plan.»

**MBQ-2. Кто отвечает за реализацию всех частей этой фичи?**
- a) Полностью наша команда — нет зависимостей от внешних сторон
- b) Частично внешняя сторона (клиент, партнёр, другая команда) — часть работы вне нашего контроля
- c) Преимущественно внешняя сторона — мы только предоставляем API/интерфейс

> Если ответ **b или c** — добавить Risk: «Delivery зависит от третьей стороны; их задержка блокирует нас».

**MBQ-3. Что должно происходить, когда фича недоступна или операция завершается с ошибкой?**
- a) Пользователь видит сообщение об ошибке и может повторить вручную — ничего не ломается
- b) Система автоматически повторяет попытку (retry с backoff) — прозрачно для пользователя
- c) Операция ставится в очередь и выполняется позже (async) — пользователь видит статус «в обработке»

**MBQ-4. Нужна ли пользователям видимость истории или лога операций?**
- a) Да — пользователь видит историю действий (когда, что, результат, кто инициировал)
- b) Нет — достаточно уведомления в момент операции, история не нужна
- c) Только для администратора — технический лог без UI для рядового пользователя

**MBQ-5. Решались ли похожие задачи в системе ранее? (Prior Art Check)**
- a) Да, есть аналогичная интеграция / функционал — нужно проверить и переиспользовать или адаптировать
- b) Частично — есть смежные механизмы (webhooks, внешние API, синхронизация), но не для этой системы/сущности
- c) Нет — это новый для нас класс задач, готовых паттернов нет

> ⚠️ Если ответ **a** или **b** — обязательно выполнить «Prior Art Analysis»: прочитать существующую реализацию, выяснить, что можно переиспользовать, что нужно расширить, и где возможны конфликты. Результат отразить в секции `## 1.4 Prior Art` PRD и в `codebase-analysis.md`. Если аналогичная интеграция уже есть — не проектировать дублирующую инфраструктуру (auth, feature flag, settings UI).

> ⚠️ **Запрет:** Ответы на MBQ-вопросы (формат «MBQ-N ответ: X»), варианты a/b/c и ход рассуждений — **не выводить в prd.md**. В PRD попадает только финальный вывод Prior Art Analysis в виде таблицы и итогового вывода (см. шаблон секции `## 1.4 Prior Art` в инструкции Step 4).

### 6b. Corner Cases — обязательная проработка

После основных вопросов явно спросить про каждую из применимых категорий edge cases. Пропустить только если категория точно нерелевантна для данной фичи.

| Категория | Вопрос для пользователя | Пример |
|-----------|------------------------|--------|
| **Пустое состояние** | Что видит пользователь, если данных ещё нет? | Список пуст, файл не загружен |
| **Одновременный доступ** | Что происходит, если двое делают одно и то же одновременно? | Race condition при бронировании, двойном сохранении |
| **Частичный сбой** | Если операция упала посередине — система в консистентном состоянии? | Клиент создан, заказ нет; файл загружен, запись в БД нет |
| **Большой объём** | Что если данных/пользователей/записей на порядок больше ожидаемого? | 10 000 позиций в списке, загрузка 100 МБ файла |
| **Права доступа** | Что если пользователь без нужных прав пытается выполнить действие? | Роль только для просмотра нажимает «Создать» |
| **Повторное выполнение** | Что если пользователь нажимает кнопку дважды или отправляет запрос повторно? | Двойная оплата, дублирование записи |
| **Устаревшие данные** | Что если данные изменились пока пользователь смотрел на страницу? | Товар пропал из наличия после открытия формы |
| **Отмена и откат** | Можно ли отменить операцию? Что восстанавливается? | Удаление с подтверждением, undo |

Для каждой применимой категории: либо добавить требование в FR, либо явно вынести в Non-Goals.

### 7. Example Topics (from cursor-prd-rules)
- Problem/Goal: «What problem does this feature solve?»
- Target User: «Who is the primary user?»
- Core Functionality: «Key actions a user should perform?»
- User Stories: «Provide user stories (As a … I want … so that …).»
- Acceptance Criteria: «Key success criteria?»
- Scope/Boundaries: «Non-goals — what should this NOT do?»
- Data Requirements: «What data to display/manipulate?»
- Design/UI: «Mockups, UI guidelines?»
- Edge Cases: «Edge cases or error conditions?»

### 8. Переход
- **Proceed только** на: «готово», «сформируй PRD», «да», «далее».
- Иначе — жди ответы или уточнения.

---

### 9. При запросе «завершить»
- Выведи детальное заключение: резюме решений, открытые вопросы, рекомендации.
- **Если prd.md уже существует** (после Step 2) — добавь секцию Conclusion в prd.md через StrReplace.
- **Если prd.md ещё не создан** (во время Step 1) — сохрани заключение; оно будет включено при создании prd.md в Step 2.
