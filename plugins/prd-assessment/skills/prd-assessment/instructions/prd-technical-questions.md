# PRD Assessment — Step 9: Technical Questions

При выполнении Step 9 пайплайна /prd-assessment — следуй этой инструкции.

## Binding Rule (§5.1)
**Каждый технический вопрос MUST cite:** Goal ID, AC, или User Story. Без ссылки — не задавать.

## Reject Rule (§5.6)
No generic tech questions («REST vs GraphQL», «which ORM») без прямой связи с конкретным AC/Goal.

## Verify-First Rule
Если ответ можно получить из кода, тестов, docstring или проектной документации — **не задавать** этот вопрос пользователю. Вместо этого зафиксировать `covered by [file/module/doc]` или включить факт в codebase context.

## Decision-Gated Rule

Step 9 останавливает пользователя только ради **реальных решений**, а не ради церемонии перехода.

Правила:
- если после Verify-first все решения закрыты локально — не задавать пользователю ни одного вопроса и автоматически передать управление в Step 10;
- если решения пользователя всё же нужны — вывести их одной пачкой (`Decision Packet`), а не серией микро-пауз;
- формальные вопросы вроде «готово?», «идём дальше?», «есть ли ещё вопросы?» запрещены.

## Input
- Business PRD (prd.md)
- Codebase analysis (codebase-analysis.md)

## Действия

### 1. Coverage Check
Перед output: для каждого критичного AC — есть ли техническое решение?
- **If no** → «AC-X: no decisions needed, covered by [file/module].»
- Покажи это перед блоком вопросов.

### 1a. Source of Truth / Convergence Check (обязательно по ситуации)

Если фича меняет статус, отношение или другое состояние, которое живёт более чем в одной подсистеме:
- определить **source of truth**;
- определить, кто запускает side-effects;
- определить, как достигается **convergence** после временного рассинхрона;
- спрашивать пользователя только то, что не удалось подтвердить локально.

### 1b. Payload / Response Contract Check (обязательно для UI/API flows)

Если фича включает frontend ↔ backend или service ↔ service контракт:
- зафиксировать точный **request envelope**;
- зафиксировать **success/error response**;
- зафиксировать, как распространяется `id` после create-path;
- зафиксировать, кто отвечает за validation / whitelist / ownership checks.

Если любой из этих пунктов остаётся двусмысленным — это Tier 1 вопрос.

### 1c. Symmetry Check (обязательно для парных действий)

Если фича содержит зеркальные действия (`like/dislike`, `add/remove`, `publish/unpublish` и т.п.):
- сравнить их по payload, auth, response, side-effects, tests и docs;
- каждую асимметрию классифицировать: intentional / legacy / gap;
- intentional — зафиксировать явно в PRD;
- legacy / gap — вынести в Tier 1 вопросы.

### 2. Output Format (§5.2)

| # | Business ref | Technical question | Codebase context |
|---|--------------|-------------------|------------------|
| 1 | AC-3 (Export PDF) | Use existing pdf-utils or add library? | lib/pdf-utils.ts exists |
| 2 | User Story 1 (Dashboard <5s) | Cache strategy for Linear API? | No caching in linear-api.js |

- У каждого вопроса — варианты (a, b, c) с обоснованием.
- **Ответ:** 1a, 2b и т.д. Пачками до 10.

### 2a. Decision Packet

Если вопросы пользователю действительно нужны, они должны быть выданы как единый пакет:
- краткий `Completeness` summary;
- список решений, которые нельзя подтвердить локально;
- варианты `a/b/c` с рекомендацией;
- явное указание, что после ответа workflow продолжится автоматически.

### 3. Prioritization (Tier)
- **Tier 1:** Scope/AC-blocking — first; max 5–7 в пачке.
  - **Main Scenario — обязательный вопрос** если `codebase-analysis.md` показывает, что самый частый продуктовый path контринтуитивен или раньше был ошибочно описан как fallback/edge case. Нужно явно зафиксировать, что является основным сценарием.
  - **Payload/response contract — обязательный вопрос** если request envelope, success/error response или ID propagation ещё не закреплены явно.
  - **Source of truth / convergence — обязательный вопрос** если локально не удалось доказать, какая система первична и как сходится внешнее состояние после временного сбоя.
- **Tier 2:** UX, performance, integrations.
  - **Performance — обязательный вопрос** если в `codebase-analysis.md` есть Architectural Finding с паттерном «Объём данных»: задать вопрос про метод backfill/миграции (`INSERT...SELECT` vs ORM), порядок операций (до/после триггеров), и допустимое время простоя. Это Tier 2, но блокирует корректность Database Changes в PRD.
  - **Инвариант включения — обязательный вопрос** если PRD вводит новую таблицу-реестр (lookup, registry, source-of-truth — таблица, агрегирующая записи из другой): явно спросить «какие записи из связанной таблицы **не** должны попадать в реестр?» (по статусу, флагу is_deleted, состоянию, типу). Без явного фильтра реализация по умолчанию включит все записи. Business ref: соответствующий FR с backfill или bulk-созданием записей.
- **Tier 3:** Infrastructure (optional).

При большем числе — следующая пачка после ответов.

### 4. Completeness Block
Перед вопросами:

```
## Completeness — Step 9: Technical Questions

| Dimension | Current | Target | Gap |
|-----------|---------|--------|-----|
| Technical questions | X% | 100% | [что осталось] |

**Осталось:** [1–2 предложения]

---
```

### 5. Output: Chat, Not PRD
- **Вопросы выводи в чат** (диалоговый режим) — пользователь видит их в сообщении и отвечает там же.
- **НЕ добавляй** в prd.md секцию «8.1 Technical Questions» и никаких других артефактов диалога.
- В Step 10 решения из ответов вносятся **в существующие разделы PRD по месту**, а не как новый раздел.

### 6. Cleanup Check (обязателен перед Step 10)

После получения всех ответов и перед переходом к Step 10 — выполнить:

1. Открыть `prd.md`.
2. Найти и **удалить**: раздел «8.1 Technical Questions», «Step 5» как заголовок, таблицы в формате `# | Business ref | Technical question`.
3. Проверить: нет ли в конце файла блока «Technical Considerations» с отдельной таблицей решений (формат `| Решение | Детали |`). Если есть — распределить каждую строку по соответствующим FR/User Story и удалить таблицу.

> Правило: prd.md — это спецификация, не лог сессии. Каждое решение живёт внутри требования, к которому относится.

### 7. Правило интеграции решений «по месту»

Каждое техническое решение из Step 5 **должно быть внесено в тот FR или раздел, которого оно касается**:

- Решение про структуру хранения → уточняет формулировку конкретного FR (например: «FR-2: TRA выполняет upsert, используя таблицу `client_external_ids` (clientId, source, externalId)»)
- Решение про аутентификацию → уточняет FR про конфигурацию/безопасность
- Решение про API-формат → вписывается в FR про endpoint
- Решение, не привязанное ни к одному FR (кросс-платформенное, инфраструктурное) → и только в этом случае — идёт в раздел **Technical Considerations** (минимально, 1–3 строки)

**Запрещено:** создавать Technical Considerations как дамп всех решений подряд.

### 8. Переход
- Если вопросы пользователю задавались — после получения ответов выполнить Cleanup Check (§6), интеграцию решений (§7) и автоматически перейти в Step 10.
- Если вопросов пользователю не было — выполнить Cleanup Check (§6), интеграцию решений (§7) и автоматически перейти в Step 10.

## Intellectual Opponent
Проверяй логику технических решений. Если вариант ведёт к противоречию с AC — укажи в обосновании.

## Проверка простоты до вопросов
Для каждого существенного архитектурного решения и блокера проверь более простой вариант и переиспользование. Подтверждённые пользователем факты учитывай в пределах их доказанности; отдельно проверяй лишь неизвестное, необходимое для реализации или обязательное по правилам проекта. Однозначные решения принимай самостоятельно; спрашивай только о реальном выборе поведения или риска.
