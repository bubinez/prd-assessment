# PRD Assessment — Step 11: PRD Self-Review

При выполнении Step 11 пайплайна /prd-assessment — следуй этой инструкции.

Шаг выполняется **агентом самостоятельно** без вопросов к пользователю, кроме редких случаев, когда действительно требуется выбор владельца.

## Input
Final PRD (`prd.md` после Step 10), `codebase-analysis.md` (если существует).

---

## Действия

### 0. Default Adversarial Stance

Self-review обязан выполняться не как формальное вычитывание, а как короткий многоролевой stress-pass даже до Step 12.
Агент действует не как "защитник решения", а как "конструктивный оппонент".

Минимальные линзы, которые агент обязан применить:
- **Скептичный архитектор:** что выглядит лишним, недоказанным или скрывает mixed-use surface?
- **QA-перфекционист:** какой edge / symmetry / convergence path не закрыт текстом PRD?
- **Новый член команды:** где документ непонятен без таблицы, диаграммы или явного baseline?
- **Вредный проджект:** какой handoff / docs / ownership хвост ещё не доведён до конца?

Если ни одна из этих линз не нашла проблему, это нужно подтвердить в summary, а не молча пропустить.

### 1. Прочитать prd.md

Открыть и прочитать полный текст `prd.md`.

Если рядом есть `codebase-analysis.md` — прочитать его тоже и использовать для проверки confirmed baseline, main scenario и docs topology.

---

### 1a. Чеклист — Confirmed vs Target

- ☐ Утверждения о **текущем** коде, тестах и документации совпадают с `codebase-analysis.md` или явно подтверждаются локальными артефактами
- ☐ Всё, что ещё не существует, но должно появиться после реализации, помечено как **целевое поведение** (`после реализации`, `целевая реализация`, `должно`)
- ☐ Основной продуктовый сценарий не назван `fallback`, `edge case`, `optional` без подтверждения из codebase-analysis

**При нарушении:** либо переписать формулировку как target-state, либо исправить PRD по confirmed baseline.

---

### 2. Чеклист — Goals

Для каждого Goal проверить:

- ☐ Описывает **состояние системы** (не результат переговоров, не процесс, не артефакт оценки)
- ☐ Содержит **число** (%, мс, кол-во, коэффициент)
- ☐ Нет запрещённых формулировок: «дать ответ», «принять решение», «оценить», «согласовать», «подготовить КП»

**При нарушении:** переформулировать Goal или удалить, если он не про систему.

---

### 3. Чеклист — Functional Requirements

Для каждого FR проверить:

- ☐ Нет слова **«или»** при описании идентификаторов, полей, форматов (должен быть выбран один вариант)
- ☐ Нет **«разумный»**, **«подходящий»**, **«настраиваемый»** без диапазона или дефолта
- ☐ Каждый FR с внешним вызовом (API, webhook, интеграция) имеет **поведение при ошибке** — явный текст или `FR-X-err`
- ☐ Нет двусмысленных формулировок, понятных только автору
- ☐ **Implicit Call Contract AC (если в codebase-analysis.md есть секция `## Implicit Call Contracts`):** для каждого контракта из этой секции — найти соответствующий FR и проверить, что AC описывает конкретный **side-effect** (DB-запись, поле, сигнал), а не только return value или «высокоуровневый» исход. Правила оценки достаточности AC — см. `rules/implicit-call-contracts.md в каталоге скилла`.
- ☐ Если FR > 7, требования сгруппированы по логическим блокам с подзаголовками
- ☐ Внутри FR нет длинных архитектурных объяснений, которые должны жить в отдельном архитектурном блоке

**При нарушении:** уточнить FR in-place через StrReplace, добавив явный side-effect assertion.

---

### 4. Чеклист — User Stories

- ☐ Есть минимум **один negative story** (сценарий ошибки / недоступности)
- ☐ Для фич типа `integration` или `backend`: есть story про retry / ручной fallback

**При нарушении:** добавить недостающую историю.

---

### 5. Чеклист — Corner Cases

Проверить, что для применимых категорий есть либо FR, либо явный Non-Goal:

| Категория | Покрыта в FR? | В Non-Goals? |
|-----------|--------------|--------------|
| Пустое состояние | | |
| Одновременный доступ (race condition) | | |
| Частичный сбой | | |
| Большой объём / нагрузка | | |
| Права доступа | | |
| Повторное выполнение (идемпотентность) | | |
| Устаревшие данные | | |
| Отмена / откат | | |

**Для каждой неохваченной применимой категории:** добавить FR или Non-Goal.

---

### 6. Чеклист — Open Questions

- ☐ Нет OQ без **владельца** (конкретная роль, не "Продукт")
- ☐ Нет OQ без **дедлайна** (дата или milestone вида "до начала CP-X.Y")
- ☐ Закрытые OQ отмечены `[Closed: ...]`
- ☐ **Закрытые OQ удалены** из таблицы (строки с `[Closed: ...]` не остаются в финальном PRD)

**При нарушении владелец/дедлайн:** назначить владельца + дедлайн, либо отметить как закрытый.

**Удаление закрытых OQ:**
- Найти все строки таблицы OQ, содержащие `[Closed:` — удалить их через StrReplace.
- Если после удаления таблица пуста (нет открытых OQ) — заменить содержимое раздела на: `*No open questions.*`
- **Не удалять** сам раздел `## 8. Open Questions` — он должен оставаться в структуре PRD.

---

### 7. Чеклист — Структура документа

- ☐ Нет раздела «8.1 Technical Questions» или блока диалога Step 5
- ☐ Нет таблицы в формате `# | Business ref | Technical question`
- ☐ Technical Considerations: ≤3 строки (только кросс-платформенные решения)
- ☐ Есть отдельный раздел `## Acceptance Criteria`
- ☐ Есть единый раздел `## Architecture & Contracts`
- ☐ Архитектурная narrative-часть не размазана по PRD без одного central block
- ☐ `Technical Considerations`, `Database Changes`, `Testing & Documentation Strategy` не дублируют архитектурный блок длинными объяснениями

**При нарушении:** удалить артефакты диалога через StrReplace.

---

### 7l. Чеклист — Acceptance Criteria

- ☐ Раздел `## Acceptance Criteria` существует
- ☐ Критерии приёмки имеют явную нумерацию `AC-N`
- ☐ Каждый критерий проверяем и сформулирован как наблюдаемое условие
- ☐ Каждый логический FR-блок или ключевой сценарий покрыт хотя бы одним AC

**При нарушении:** добавить или перегруппировать критерии приёмки через StrReplace.

---

### 7m. Чеклист — Architecture Consolidation

Если фича меняет runtime, boundaries, integration surface, source of truth, async flow или API contracts:

- ☐ Весь архитектурный narrative-материал собран в `## Architecture & Contracts`
- ☐ В этом разделе есть boundaries / owned state / source of truth / execution surface / contracts / docs topology
- ☐ Другие разделы либо ссылаются на архитектурный блок, либо содержат только свой слой, без повторного архитектурного эссе

**При нарушении:** собрать архитектурный материал в единый блок и убрать размазывание по соседним разделам.

---

### 7c. Чеклист — Execution Surface / Analytical Debt

- ☐ В PRD отражены выводы из `Execution Surface Matrix`, если фича затрагивает async/multi-component surface
- ☐ Нет неотражённых mixed-use task / queue / worker / callback path
- ☐ `Analytical Debt Register` не содержит хвостов, которые уже должны были быть закрыты к Step 10

**При нарушении:**
- если это локальная недостающая формулировка — исправить PRD;
- если найден новый `adjacent path`, `mixed-use surface`, `main scenario` или конфликт source of truth — вернуть статус `rewind_required`.

---

### 7d. Чеклист — Артефакты процесса (Process Artifacts)

Проверить весь текст prd.md на наличие следов внутреннего процесса assessment. Финальный PRD — документ для разработчиков и стейкхолдеров; он должен содержать только решения, требования и оценки.

**Запрещённые паттерны:**

| Паттерн | Пример нарушения | Действие |
|---------|-----------------|----------|
| Ссылка на MBQ-ответ | `MBQ-5 ответ: b) — Частично` | Удалить строку целиком |
| Ссылка на шаг пайплайна в заголовке | `(из Business Clarification)`, `(из Step 5)` | Убрать скобочную часть из заголовка |
| Упоминание закрытых OQ по номеру | `OQ-1 и OQ-3 закрыты — оценки твёрдые` | Удалить фразу; если нужно — переформулировать как факт: «все вопросы закрыты» или убрать совсем |
| Ход рассуждений вместо решения | `ниже — анализ существующих решений и решение о переиспользовании` | Удалить; оставить только таблицу/вывод |
| Варианты a/b/c из диалога Step 1/5 | `a) …; b) …; c) …` вне контекста Non-Goals | Удалить; оставить только выбранное решение |
| Метки Completeness-блока | `Requirements clarity: 75%` | Удалить |
| Служебные комментарии агента | `// TODO: уточнить`, `[PLACEHOLDER]`, `[TBD — ответить на Step 5]` | Удалить или заменить финальным значением |
| Внутренние пометки процесса | `[resume checkpoint]`, `[scope changed]` | Удалить |
| **«Приложение:» / «Note:» с отсылкой на шаг** | `Приложение: механизм будет определён в Step 5` | Удалить; вписать итоговое решение прямо в FR или оформить явным OQ |
| **Вводная фраза к TC без содержания** | `На основе анализа кодовой базы приняты следующие решения:` | Удалить вводную фразу; TC должен начинаться с конкретного **TC-N: Название** |
| **«Опциональные» OQ с known defaults** | `OQ-6 (опционально): Порт health endpoint (default: 8080)` | Удалить OQ; default вписать прямо в FR (например, `:8080/health`) |
| **Закрытые OQ, оставшиеся в таблице** | OQ с ответом `Решено в TC-X` или `C (Hybrid)` в столбце «Решение» | Удалить строку; решение уже должно быть в FR/TC |

**Действие:** для каждого найденного паттерна — удалить или заменить финальным текстом через StrReplace. Если после удаления абзац становится пустым — удалить абзац целиком.

### 7e. Чеклист — Terminology Audit

Проверить, что PRD не использует терминологию, искажающую реальную систему.

- ☐ `fallback`, `edge case`, `optional` не используются для основного продуктового сценария
- ☐ `already`, `existing`, `protected`, `guaranteed`, `symmetric` употреблены только там, где это подтверждено codebase-analysis или кодом
- ☐ Не вводятся новые архитектурные термины, которых нет в системе (`signals`, `event bus`, `managed sync` и т.п.), если фактически используются другие механизмы

**При нарушении:** заменить термин на точное описание факта или целевого состояния.

---

### 7f. Чеклист — Язык документа (Russian Language)

Весь PRD должен быть написан **исключительно на русском языке** (кроме технических исключений).

**Проверка:**
- ☐ Все разделы (Goals, FR, User Stories, Non-Goals, Open Questions, Risks) — на русском
- ☐ Все описания в diagrams (node labels, edge labels, notes) — на русском
- ☐ Все таблицы (Change Plan, Field Mapping) — заголовки и значения на русском

**Допустимое использование английского:**
- Имена переменных, функций, методов: `user_id`, `get_token()`
- Технические термины без русского аналога: `JSON`, `REST API`, `webhook`, `OAuth2`
- Названия внешних систем/сервисов: `Telegram`, `CRM Битрикс`, `Google Drive`
- Математические обозначения и формулы

**При нарушении:** если ≥10% текста (абзацов, фраз) на английском — переписать на русский через StrReplace. Примеры замен:
- `User should receive email notification` → `Пользователь должен получить email-уведомление`
- `Handle timeout gracefully` → `Корректно обрабатывать таймаут`
- `Rate limit: 100 requests per minute` → `Rate limit: 100 запросов в минуту`

**Действие:** сканировать весь текст; при нарушении — заменить через StrReplace.

Если фича меняет runtime-контракт, API, важный helper или пользовательский поток:

- ☐ В PRD определён хотя бы один **канонический** документ для финального runtime-контракта
- ☐ Supporting docs и historical/assessment docs различены явно
- ☐ В разделе Documentation Updates есть задача на **contradiction cleanup** между `Doc/`, `docs/` и `ai_docs/`

### 7b. Чеклист — Design Considerations (при наличии UI-работы)

- ☐ Секция **Design Considerations** в prd.md **не пустая** и не содержит только «optional» / «N/A»

- ☐ Если макеты/дизайн отсутствуют — в **Open Questions** есть OQ с владельцем и дедлайном: «Кто и когда создаёт дизайн?»

**При нарушении:**
- Если Design Considerations пустые — добавить OQ: «Design: Wireframes and UI mockups are not provided. Who is responsible and what is the deadline? Owner: [Designer/Product], Deadline: before CP-1.1»

- ☐ Нет placeholder-комментария `⚠️ Диаграммы будут добавлены` — если он остался, значит Step 10 не заполнил диаграммы
- ☐ Для `integration`: есть sequence diagram (поток данных) и component diagram
- ☐ Для `architecture`: есть component diagram
- ☐ Секция `## Diagrams` существует в prd.md
- ☐ Нет placeholder-комментария `⚠️ Диаграммы будут добавлены` — если он остался, значит Step 10 не заполнил диаграммы
- ☐ Для `integration`: есть sequence diagram (поток данных) и component diagram
- ☐ Для `architecture`: есть component diagram
- ☐ Каждый блок ` ```mermaid ` закрыт соответствующим ` ``` `

### 7i. Чеклист — Database Changes

Применяется ко всем типам фич (`backend`, `integration`, `architecture`, `UI-only`).

- ☐ Секция `## Database Changes` (или `## 7a. Database Changes`) существует в prd.md
- ☐ Раздел **не пустой** и не содержит placeholder (`[TBD]`, `[заполнится в Step 10]`)
- ☐ Если фича затрагивает БД: перечислены конкретные изменения (таблицы, поля, индексы, миграции)
- ☐ Если фича **не** затрагивает БД: явно написано «No database changes required.»
- ☐ **Backfill check:** если создаётся новая таблица, которая является lookup/index/реестром для существующих данных (например, `VacancySource`, `VacancyPartitionMap`, `UrlLookup`) — убедиться, что в миграции есть `RunPython` бэкфилл, заполняющий её из существующих данных. Отсутствие бэкфилла для таблицы-реестра = критический баг деплоя.

**При нарушении:**
- Раздел отсутствует → создать и заполнить на основе FR и `codebase-analysis.md`.
- Раздел содержит placeholder → заполнить или указать «No database changes required.»
- Раздел есть, но неконкретный (нет названий таблиц/полей) → уточнить или добавить OQ с владельцем и дедлайном.
- Отсутствует backfill для таблицы-реестра → добавить FR с описанием `RunPython` бэкфилла (источник данных, фильтр, batch size, `ignore_conflicts=True`).

### 7j. Чеклист — Markdown Rendering

Проверить весь текст `prd.md` на паттерны, которые Markdown-рендерер интерпретирует иначе, чем задумано.

**Паттерны нарушений:**

| Паттерн | Пример нарушения | Почему ломается | Исправление |
|---------|-----------------|-----------------|-------------|
| Одиночная тильда `~` вокруг текста | `~0.6 спринта (~6 рабочих дней)` | Вторая `~` закрывает первую → ~~зачёркивание~~ | Заменить на `≈` или экранировать: `\~` |
| Незакрытый `*` или `_` внутри слова | `_build_системы` | Может сформировать курсив там, где не нужно | Экранировать: `\_build\_` |
| Незакрытые обратные кавычки `` ` `` | `код без закрывающей кавычки | Весь следующий текст превращается в code span | Добавить закрывающую кавычку |
| `>` в начале строки без намерения цитирования | строка начинается с `> текст` случайно | Рендерится как blockquote | Убрать `>` или добавить пробел |
| HTML-сущности в таблицах | `<br/>`, `&nbsp;` в ячейках таблицы | Ломают рендеринг в некоторых рендерерах | Заменить на пробел или `\n` вне таблицы |

**Алгоритм проверки тильд (наиболее частая ошибка):**

Для каждой строки, содержащей `~`:
1. Подсчитать количество одиночных `~` (не `~~`) в строке.
2. Если количество нечётное или ≥2 одиночных `~` в одной строке — **потенциальное зачёркивание**.
3. Проверить: является ли `~` символом «приблизительно» (перед числом: `~50%`, `~6 дней`, `~0.6 спринта`) — заменить на `≈`.
4. Если `~` — намеренное зачёркивание (`~~текст~~`) — оставить как есть (двойная тильда).

**При нарушении:** заменить через StrReplace по конкретному месту нарушения.

### 7k. Чеклист — References

Применяется, если в prd.md есть раздел `## References` (или аналогичный).

- ☐ **Каждая ссылка имеет URL** — формат `[Название](https://...)` или явный путь к файлу
- ☐ **Ссылки без URL удалены** — исключение см. ниже

**Правило удаления:**
Удалить строку из References, если она:
1. Не содержит кликабельной ссылки (URL в скобках или явного пути к файлу), **И**
2. Не является ссылкой на документ анализируемого проекта

**Исключение — сохранять без URL**, если строка ссылается на внутренний документ анализируемого проекта:
- Внутренние PRD проекта (`PRD NN — ...` без URL — документы существуют внутри команды)
- Blueprint-ы и spec-файлы из `ai_docs/` того же проекта
- Любой документ, путь или название которого явно привязан к кодовой базе из Step 3/4

**Действие:** удалить строки-нарушители через StrReplace. Если раздел References становится пустым — удалить весь раздел.

> **Примеры:**
> - `- [SugarCRM API](https://apidocs.sugarcrm.com/)` → **оставить** (есть URL)
> - `- PRD 04 — Client Management (power-rent)` → **оставить** (внутренний документ проекта)
> - `- Blueprint: external-automation.md` → **оставить** (внутренний документ проекта)
> - `- Some article about REST APIs` → **удалить** (нет URL, не внутренний документ)

## Контракт выхода

Кроме обычного `pass with fixes` / `pass without changes`, subagent может вернуть:

- `rewind_required` — если в ходе self-review обнаружен:
  - новый `main scenario`;
  - новый `adjacent path`;
  - новый `mixed-use task / queue / worker`;
  - новый конфликт `source of truth / convergence / docs topology`.
- `decision_required` — если найдено спорное место, которое нельзя закрыть ни механической правкой, ни rewind'ом и действительно требует выбора пользователя.
- При `decision_required` subagent обязан вернуть `questions_for_user`:
  - `observed`
  - `why_it_matters`
  - `question`
  - `options`
- Молчаливые допущения по same-class sibling feature, границе scope или спорной boundary запрещены.

При `rewind_required` основной flow обязан:
1. вернуться в Step 5;
2. затем заново пройти Step 9;
3. обновить Step 10;
4. и только потом повторить Step 11.

## Проверка соразмерности
Перед итогом проверь каждый существенный FR, алгоритм, статус, экспериментальный блокер, тест и пункт плана: какую цель или конкретный риск он покрывает, можно ли проще с существующими средствами? Устрани однозначную избыточность с синхронизацией связанных разделов; реальные изменения scope/поведения передай как decision_required. Не удаляй требования пользователя, проектные правила и существенные проверки безопасности и корректности. Отсутствие проблемы обоснуй на конкретных пунктах.
