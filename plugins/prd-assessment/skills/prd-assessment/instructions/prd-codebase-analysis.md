# PRD Assessment — Step 4: Codebase Analysis

При выполнении Step 4 пайплайна /prd-assessment — следуй этой инструкции.

## Input
Подтверждённый project path (из Step 3).

---

## Действия

### 1. Validate Path
- Если path invalid/empty — report error; спроси корректный путь или «пропустить».
- **Degraded:** user подтвердил skip → proceed с пустым Technical Appendix; flag в PRD.

### 2. Analyze
- **Structure:** folders, key files
- **Dependencies:** package.json, requirements.txt, go.mod, pyproject.toml
- **README:** обзор проекта
- **Entry points:** main, app entry, CLI
- **Shared utils:** общие модули
- **Test setup:** структура тестов
- **Build/deploy config:** конфигурация сборки

### 2a. Baseline Reality Check (обязательно)

Перед выводами о целевой реализации отделить:

| Категория | Что зафиксировать |
|-----------|-------------------|
| **Confirmed baseline** | Что уже существует в коде, тестах, docstring или проектной документации |
| **Partial baseline** | Что реализовано частично или асимметрично |
| **Missing** | Чего в системе действительно нет |
| **Target state** | Что должно появиться после реализации |

Правила:
- Любое утверждение, которое можно проверить локально, **нужно проверить сейчас**, а не оставлять как «проверим потом».
- Если Business PRD описывает target-state как текущий baseline — отметить это как расхождение для Scope Checkpoint.
- Если продуктовый основной path выглядит контринтуитивно (например, технически сложный, но встречается чаще всего) — явно отметить его как **main scenario**, а не fallback/edge case.

### 2b. Runtime Documentation Check (обязательно для критичных helper/API/status-contract)

Для критичных runtime-контрактов и helper-ов проверить:
- есть ли **docstring** на самом методе/классе;
- есть ли описание в `Doc/`, `docs/` или `docs/`, `ai_docs/`;
- какие документы являются **canonical**, какие **supporting**, какие **historical/assessment**;
- есть ли противоречия между кодом, тестами и документацией.

Если документация уже существует, но расходится с кодом — зафиксировать это как documentation drift, а не как открытый вопрос к пользователю.

### 3. Map
- Где новая фича впишется
- Integration points
- Constraints: frameworks, conventions, лимиты

### 3a. Adjacent Scope Check (обязательно)

До углубления в поздние шаги агент обязан собрать дешёвый `scope radar`, а не молча продолжать с первым найденным surface.

Нужно явно выделить:

| Категория | Что зафиксировать |
|-----------|-------------------|
| **Primary surface** | Что точно входит в scope по текущей постановке |
| **Adjacent similar surfaces** | Соседние feature того же класса, которые выглядят похожими по смыслу или механике |
| **Shared runtime surfaces** | Общие pipeline/task/status/fallback/orchestration seams |
| **Scope forks** | Где выбор include/exclude/defer меняет PRD и поздние шаги |

Правила:
- Искать не только adjacent paths, но и **same-class sibling flows**.
- Если найдена sibling feature с общими runtime/pipeline/status semantics, агент обязан вынести её в Scope Checkpoint даже если пользователь её не назвал.
- Запрещено молча делать допущение `это, наверное, вне scope`, если позднее это приведёт к rerun Step 11/12/14.
- Вопросы пользователю допустимы только для реального выбора границы scope, а не для фактов, которые можно найти в коде.

### 3b. External System Analysis (для `integration` — обязательно; для `backend`/`architecture` — если есть внешние зависимости)

Если Feature Classification = `integration` **или** PRD содержит упоминания внешних API / сторонних сервисов:

#### Когда выполнять

- **Обязательно:** Feature Classification = `integration`.
- **По необходимости:** `backend` или `architecture`, если в FR/Goals упоминается внешний сервис, API, webhook от третьей стороны.
- **Пропустить:** `UI-only` или фичи без внешних зависимостей.

#### Источники информации

Агент **должен** попытаться получить информацию из всех доступных источников (в порядке приоритета):

1. **Документация в проекте:** `docs/`, `ai_docs/`, README — ищи упоминания внешнего сервиса.
2. **Существующие интеграции в коде:** grep по имени сервиса, URL паттернам, SDK импортам.
3. **Публичная документация API:** если URL документации известен или выводим из названия сервиса — использовать WebFetch / WebSearch для получения:
   - Base URL, версионирование API
   - Аутентификация (API key, OAuth2, JWT, Basic)
   - Rate limits / throttling
   - Формат данных (JSON, XML, SOAP)
   - Pagination
   - Webhook support (входящие/исходящие)
4. **Пользователь:** если документация недоступна или закрыта — спросить: «Есть ли у вас документация API [сервиса]? Прикрепите файл или дайте URL.»

#### Что анализировать

Для каждой внешней системы, упомянутой в PRD:

| Аспект | Что выяснить | Влияние на PRD |
|--------|-------------|----------------|
| **Аутентификация** | Тип (API key, OAuth2, JWT); нужен ли refresh; кто выдаёт credentials | → FR: хранение секретов, ротация токенов |
| **Rate limits** | Запросов в минуту/час; burst limits; что при превышении (429, backoff) | → FR: throttling, очередь, retry strategy |
| **Формат данных** | JSON / XML / SOAP / GraphQL; encoding; max payload size | → FR: маппинг полей, валидация, трансформация |
| **Версионирование** | Текущая версия API; deprecation policy; breaking changes history | → Risk: API может измениться; FR: версию зафиксировать |
| **Sandbox / тестовая среда** | Есть ли sandbox; отличия от production; нужен ли отдельный ключ | → Change Plan: задача на настройку sandbox |
| **Доступность / SLA** | Uptime гарантии; что при downtime; maintenance windows | → FR: fallback, retry; Risk: внешняя зависимость |
| **Webhook support** | Есть ли webhooks; формат callback; retry policy провайдера | → FR: webhook handler, HMAC верификация |
| **Pagination** | Тип (offset, cursor, page); max items per page | → FR: обработка больших объёмов данных |
| **Error format** | Структура ошибок; коды; human-readable messages | → FR: маппинг ошибок, логирование |
| **SDK / библиотеки** | Есть ли официальный SDK для нашего стека; качество; maintenance | → Technical decision: SDK vs raw HTTP |

#### Degraded

- Публичная документация недоступна → спросить у пользователя URL или файл.
- Пользователь не предоставил → зафиксировать как **OQ с владельцем и дедлайном** в prd.md: «External API documentation for [service] is not available. Owner: [PM/Tech Lead], Deadline: before CP-0.x».
- Частичная информация → зафиксировать что известно; неизвестное → OQ.

### 3c. Prior Art Analysis (если MBQ-5 = a или b)

Если в ответе на MBQ-5 пользователь указал, что похожие задачи решались ранее:

1. **Найти существующие реализации:** grep по ключевым словам фичи (название сервиса, тип интеграции, название сущности), просмотреть `pages/api/integrations/`, `lib/`, `docs/`.
2. **Проанализировать каждую найденную реализацию:**

| Аспект | Что зафиксировать |
|--------|-------------------|
| **Где находится** | Путь к файлу/папке |
| **Что делает** | Краткое описание (1–2 строки) |
| **Механизмы** | Auth, feature flag, settings UI, webhook, error handling |
| **Статус** | Активна в production / устаревшая / экспериментальная |
| **Переиспользование** | Что можно взять as-is, что адаптировать, что нельзя |
| **Конфликты** | Есть ли риск пересечения (дублирование endpoint, таблицы, флагов) |

3. **Вывод:** если аналогичная инфраструктура уже есть — **не проектировать заново**; зафиксировать в `prd.md` (секция `## 1.4 Prior Art`) и в `codebase-analysis.md` (секция `## Prior Art`).

> ⚠️ **Формат секции `## 1.4 Prior Art` в prd.md — только финальный вывод:**
> - Таблица существующих механизмов (Существующий механизм | Статус | Переиспользование в данной фиче).
> - Итоговый вывод: одно-два предложения о принятом решении.
> - **Запрещено:** вставлять ответы на вопросы MBQ (формат «MBQ-N ответ: X»), варианты a/b/c, объяснение хода анализа, фразы типа «ниже — анализ» или «решение о переиспользовании». PRD должен содержать решения, а не ход рассуждений.

> ⚠️ Если Prior Art выявлен, но пользователь не отвечал на MBQ-5 — всё равно добавить в Scope Checkpoint: «Обнаружена аналогичная реализация: [путь]. Требует ли она переиспользования или изменений?»

### 3c.1. Request Path Audit (для `integration`, `architecture` — обязательно)

Если Feature Classification = `integration` или `architecture` **и** фича вводит новый домен, proxy, CDN или меняет routing запросов:

#### Цель

Убедиться, что **каждый тип запроса** пользователя явно приписан к конкретному серверу/домену. Предотвращает ситуацию, когда часть ресурсов остаётся на старом сервере и не проходит через proxy.

#### Алгоритм

1. Выписать все **типы ресурсов**, которые запрашивает клиент (браузер/приложение): HTML-страницы, JS/CSS/images, API-вызовы, WebSocket, media.
2. Для каждого типа — нарисовать полный путь: клиент → каждый hop (домен, протокол, сервис) → финальный ответ.
3. Отметить хопы, которые **меняются** из-за фичи (переходят на новый домен/proxy).
4. Проверить хопы, которые фича **не затронула**: они явно должны оставаться на старом сервере по замыслу — или это gap?
5. Проверить: нет ли ссылок в HTML/JS/CSS (включая `{% static %}`, hardcode'd URLs, `STATIC_URL`), которые указывают на старый домен и не учтены в изменениях.

#### Результат

Секция `## Request Path Audit` в `codebase-analysis.md` — таблица:

| Тип ресурса | Текущий путь | Новый путь (после фичи) | Изменяется? | Gap? |
|-------------|-------------|------------------------|-------------|------|
| HTML (Web App страница) | browser → MAIN_DOMAIN → Django | browser → PROXY_DOMAIN → cmd/proxy → Django | ✅ | — |
| JS/CSS статика | browser → MAIN_DOMAIN/static/ → Django | browser → PROXY_DOMAIN/app/static/ → Nginx (диск) | ✅ | — |
| API вызов | browser → MAIN_DOMAIN/api/ → Django | browser → PROXY_DOMAIN/bot/api/ → cmd/proxy → Django | ✅ | — |
| `{% static %}` ссылки в templates | генерируются как `/static/bot/...` | нужен `STATIC_URL = /app/static/` | ✅ | проверить |

**Симптом пропуска:** после деплоя часть запросов идёт напрямую на основной сервер, минуя proxy.

### 3d. Architectural Inefficiency Analysis (для `backend` и `architecture` — обязательно)

Если Feature Classification = `backend` или `architecture` — проанализировать, не затрагивает ли фича участки кода с архитектурными неэффективностями, которые стоит исправить попутно.

#### Цель

Выявить паттерны, где текущая реализация работает, но неоптимальна по стоимости, производительности или сложности — и где фича создаёт естественную точку для рефакторинга.

#### Что искать

| Паттерн | Примеры | Как искать |
|---------|---------|------------|
| **Дублирование вычислений** | Одни и те же данные вычисляются несколько раз в одном pipeline (например, эмбеддинги, дорогие SQL-запросы) | Трассировать путь данных от input до output; искать повторные вызовы одних функций с теми же аргументами |
| **Выбрасываемые результаты** | Результат дорогого вычисления используется только для промежуточной проверки, затем выбрасывается, и похожий результат вычисляется заново | Искать функции, чей return value не сохраняется и не передаётся дальше |
| **Неправильный уровень абстракции** | Логика находится в неподходящем месте (например, ML-вычисления в web-процессе, I/O в синхронном контексте) | Искать вызовы тяжёлых операций в контекстах без worker'ов |
| **Избыточные roundtrip'ы** | N+1 запросов к БД, повторные HTTP-вызовы к одному endpoint | `select_related`/`prefetch_related` отсутствие; httpx/requests в цикле |
| **Смешение ответственностей** | Один модуль делает несколько несвязанных вещей, что усложняет изменение каждой из них | Искать классы/функции с несколькими независимыми обязанностями |
| **Объём данных — операционный риск** | Фича затрагивает таблицу с большим числом строк (>50k): backfill, ALTER TABLE, массовый UPDATE, создание индекса | Проверить размер таблиц из `codebase-analysis` (счётчики, логи, вакансии, события). Если фича меняет схему или данные такой таблицы — обязательно зафиксировать в Architectural Findings с оценкой объёма и рекомендуемым методом (SQL-side vs ORM) |

#### Алгоритм

1. Для каждого модуля, который фича **читает или модифицирует** — проследить полный data flow через него.
2. Задать вопрос: «Какие дорогие операции выполняются в этом пути?» (DB, ML-inference, HTTP, CPU-bound)
3. Задать вопрос: «Эти операции выполняются ровно столько раз, сколько необходимо?»
4. Если нет — зафиксировать как **Architectural Finding** (см. формат Output).
5. **Writer-map (обязательно для `backend`/`architecture` при изменении схемы БД):** для каждой таблицы, которую PRD создаёт, изменяет или вводит инварианты для — найти **все места в кодовой базе**, которые пишут в неё (services, management commands, admin, migrations, signals, Celery tasks). Grep по имени модели и имени таблицы. Цель: убедиться, что новый инвариант (фильтр, ограничение, правило включения) соблюдается во **всех** writer-ах, а не только в основном сервисе. Несоответствующие writer-ы → выводить в Scope Checkpoint как затронутые файлы.

#### Правило эскалации (ОБЯЗАТЕЛЬНО)

Если найдена архитектурная неэффективность:

1. **Не добавлять в scope текущего PRD автоматически.**
2. **Не предлагать костыль** (например, «кэшировать результат в переменную» вместо правильного рефакторинга).
3. Зафиксировать в `codebase-analysis.md` в секции `## Architectural Findings`.
4. В **Scope Checkpoint** явно сообщить пользователю о найденной неэффективности и предложить варианты:

```
## Архитектурная неэффективность: [название]

Обнаружено: [описание проблемы, например: «эмбеддинги вычисляются дважды: в soft dedup (deduplication.py:72) и в классификации (vacancies.py:1473) — разный текст, разные цели, но одна и та же дорогая операция»]

Варианты:
a) Исправить архитектурно — вынести в отдельный фокус или включить в scope текущего PRD как отдельную фазу
b) Зафиксировать как техдолг — добавить в Risk Register и создать отдельный assessment позже
c) Оставить как есть — если текущее поведение обосновано

Ваш выбор?
```

5. При выборе **a** — дождаться согласия пользователя, затем расширить scope PRD или создать отдельный assessment.
6. При выборе **b** — добавить в Risk Register PRD с пометкой «Техдолг».
7. При выборе **c** — зафиксировать обоснование в `codebase-analysis.md`.

> ⚠️ **Запрещено:** предлагать workaround вместо правильного решения. Если архитектура требует исправления — исправлять её полностью с разрешения пользователя, а не латать.

### 5. Scope Checkpoint (→ Step 2)

После сохранения `codebase-analysis.md` — обязательно выполнить:

1. Сформулировать **список изменений картины** относительно Business PRD из Step 2:
   - Новые технические ограничения (например: "используемая библиотека не поддерживает X")
   - Несовместимости (например: "существующая схема БД конфликтует с предложенным подходом")
   - Упрощения (например: "нужный модуль уже существует, объём меньше ожидаемого")
   - Расхождения между confirmed baseline и target-state формулировками в PRD
   - Main scenario, который был ошибочно описан как fallback/edge case
   - Документационные противоречия и необходимость выбрать canonical doc
   - Same-class sibling flows, которые обнаружены в коде и требуют явного include/exclude
   - Shared runtime surfaces, по которым ещё не принято решение о границе scope

2. Вывести пользователю:
   ```
   ## Scope Checkpoint (Step 4 → Step 2?)
   
   Анализ кодовой базы выявил:
   - [список изменений, если есть]
   - [Adjacent similar surfaces / same-class sibling flows, если есть]
   
   Это влияет на scope или Goals из PRD?
   - a) Да — нужно пересмотреть Goals/FR (вернуться в Step 2)
   - b) Нет — продолжить в Step 5
   ```

   Если обнаружен sibling flow того же класса, checkpoint обязан содержать короткий decision-shaped вопрос в таком формате:

   ```text
   Вижу ещё [Sibling Feature]: она использует похожий [runtime/pipeline/status] surface.
   Включаем её в scope этого PRD или фиксируем как explicit out-of-scope?
   ```

3. При ответе **a** → выполнить Step 2 (ревизия prd.md), затем продолжить в Step 5.
4. При ответе **b** → продолжить в Step 5.

> Если изменений нет — всё равно вывести checkpoint с «изменений не выявлено» и спросить подтверждение.

### 6. Degraded
- Path invalid и user не подтвердил skip → **Critical stop**.
- Analysis частично failed → сохрани что удалось; flag в PRD.

- 80% — External Systems проанализированы (для `integration`) или N/A
