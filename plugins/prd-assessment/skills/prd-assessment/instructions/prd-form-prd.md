# PRD Assessment — Step 2: Form Business PRD

При выполнении Step 2 пайплайна /prd-assessment — следуй этой инструкции.

## Input
Ответы пользователя из Step 1.

---

## Действия

### 1. Создать папку
- Путь: каталог из `.agent/config.json` → `documentation.paths.prdAssessment` (если настройка отсутствует, используй принятую в проекте папку документации или `docs/`) + `<feature-slug>/`, где feature-slug — латиница, дефисы.
- Извлеки feature slug из описания (латиница, дефисы).
- **Duplicate Guard:** проверь, не существует ли уже папка `docs/<feature-slug>/` для этой фичи. Если найдена — **не создавать вторую папку**; сообщи пользователю и продолжи работу в существующей папке.
- Создай папку `docs/<feature-slug>/`, если не существует.

### 2. PRD Structure (§6 cursor-prd-rules)

Единый файл `prd.md`. Содержит:

1. **Introduction/Overview** — feature, problem, goal
2. **Goals** — specific, measurable objectives
3. **User Stories** — narratives (As a … I want … so that …)
4. **Functional Requirements** — numbered, explicit; технические решения из Step 9 вписываются сюда «по месту»
   - Если FR больше 7, они **обязательно** группируются по смысловым блокам.
   - Допустимые типы блоков: `Core Flow`, `State & Contracts`, `Integrations`, `UI/UX`, `Security`, `Observability`, `Migration / Compatibility`.
   - Внутри блока FR остаются пронумерованными глобально (`FR-1`, `FR-2`, ...), но перед ними должен быть подзаголовок блока.
   - FR должны описывать **поведение и контракт**, а не длинные архитектурные объяснения.
5. **Acceptance Criteria** — *обязательный раздел*; критерии приёмки, привязанные к FR-группам или ключевым сценариям.
   - Для каждого логического блока FR должен быть хотя бы один критерий приёмки.
   - Формат: нумерованный `AC-N` с явной проверяемой формулировкой.
6. **Architecture & Contracts** — *обязательный единый архитектурный блок*.
   - В этом разделе концентрируется вся архитектурная narrative-часть: boundaries, runtime flow, source of truth, contracts, ownership, convergence, execution surface, canonical docs.
   - Архитектурные объяснения не должны быть размазаны по `Technical Considerations`, `Database Changes`, `Testing`, `Open Questions`.
   - Другие разделы могут ссылаться на этот блок, но не должны дублировать его narrative.
7. **Design Considerations** — mockups, UI/UX (optional)
7a. **Diagrams** — архитектурные/потоковые диаграммы (см. §3d ниже)
8. **Technical Considerations** — *опционально*; только кросс-платформенные решения без привязки к FR и без дублирования архитектурного блока (1–3 строки max). Если все решения влезли в FR и `Architecture & Contracts` — раздел не создавать или оставить пустым.
8a. **Database Changes** — *обязательный раздел*; описывает все изменения схемы БД: новые таблицы/колонки, удаляемые поля, изменения индексов, миграции. Если фича не затрагивает БД — явно указать «No database changes required». Финально заполняется в Step 10 на основании анализа Step 4 и решений Step 9. В Step 2 — оставить placeholder.
    Для задач с **backfill или data migration** — обязательно указать:
    - ожидаемый объём строк (порядок величины);
    - метод: `INSERT INTO ... SELECT` / `UPDATE ... FROM` на стороне БД (предпочтительно при >50k строк) vs Python ORM итерация (допустимо при <50k строк);
    - порядок операций: массовые UPDATE/INSERT должны идти **до** создания триггеров, CHECK constraints и FK — иначе каждая изменяемая строка вызывает триггер, что на 1M+ строк умножает время миграции на порядок.
9. **Testing & Documentation Strategy** — *обязательный раздел*; strategy, verification matrix, docs updates
10. **Success Metrics** — how to measure success
11. **Open Questions** — remaining unknowns
12. **Change Plan** — placeholder; заполнится в Step 14

**Target audience:** Junior developer. Unambiguous, minimal jargon.

### 3. Edit-in-Place
- **Create:** Write при первом создании файла `prd.md`.
- **Update:** StrReplace для последующих правок.
- **Запрещено:** draft-prd.md, prd-v2.md, prd-final.md, копии. Все рабочие файлы складываются в папку `<assessment-dir>/<feature-slug>/` с понятным названием, отражающим содержимое. Основные имена: `prd.md`, `codebase-analysis.md`, `<feature-slug>-plan.md`, `<feature-slug>-tasks.md`.

### 3a. Guard Rails — Язык (Russian Language)

Весь PRD **обязательно на русском языке**. Исключения — только для технических терминов без аналога (JSON, REST API, OAuth2, имена переменных).

**Проверка перед записью:**
- ☐ Заголовки всех разделов на русском
- ☐ Все Goals, FR, User Stories, Non-Goals — на русском
- ☐ Описания в таблицах и диаграммах — на русском

Если обнаружен текст на английском (≥ одна фраза) — переписать на русский.

> Полный чеклист языка — в Step 11: `prd-self-review.md §7f`.

### 3b. Guard Rails — Артефакты процесса

Перед записью любого текста в prd.md убедиться, что в него **не попадают** следы внутреннего процесса:

- Ответы на MBQ-вопросы (формат `MBQ-N ответ: X`) — в PRД попадает только итоговый вывод
- Ссылки на шаги пайплайна в заголовках: `(из Business Clarification)`, `(из Step 5)` — убрать скобочную часть
- Упоминания закрытых OQ по номеру: `OQ-1 и OQ-3 закрыты` — не писать в PRД
- Ход рассуждений: `ниже — анализ`, `решение о переиспользовании` — писать только вывод
- Варианты a/b/c из диалога Step 1/5 — писать только выбранное решение
- `[PLACEHOLDER]`, `[TBD]`, Completeness-метки — не оставлять в файле
- **«Приложение:» / «Note:» / «Примечание:»** с отсылкой на будущий шаг («будет определено в Step 5», «определяется в codebase-analysis») — **ЗАПРЕЩЕНО**. Если решение ещё неизвестно — оформить явным OQ с владельцем и дедлайном, либо вписать решение сразу по месту.
- **Формулировки вида «На основе анализа ... приняты следующие решения»** — не писать; решения вписывать прямо в FR или TC без вводных фраз.
- **OQ с пометкой «опционально»** или «детали для Step 9» — не допускаются; либо решить явно, либо удалить.
- **Неподтверждённый baseline как факт** — запрещён. Если текущее поведение кода/документации ещё не подтверждено Step 4, нельзя писать его как уже существующий факт; использовать формулировку целевого состояния (`целевое поведение реализации`, `после реализации`) или оставить нейтральное описание проблемы.

> Полный список паттернов и действий — в Step 11: `prd-self-review.md §7d`.

### 3c. Guard Rails — Goals

Перед записью Goals в prd.md проверь каждый Goal по чеклисту:

- ☐ Goal описывает **измеримое состояние системы** (не процесс, не результат переговоров, не результат оценки)
- ☐ Метрика содержит **число** (%, мс, кол-во, коэффициент)
- ☐ Запрещённые формулировки в тексте Goal: «дать ответ», «принять решение», «оценить», «согласовать», «подготовить КП»

Если Goal нарушает любой пункт — переформулировать или удалить.

### 3ca. Guard Rails — FR Grouping / Acceptance / Architecture Block

Перед записью структуры PRD проверить:

- ☐ Если FR > 7, раздел `Functional Requirements` разбит на логические блоки с подзаголовками
- ☐ Раздел `Acceptance Criteria` существует и покрывает все ключевые FR-блоки
- ☐ Раздел `Architecture & Contracts` существует как единый блок
- ☐ Архитектурные объяснения не размазаны narrative-текстом по нескольким дальним разделам без central section

Правила:
- `Functional Requirements` — это требования и контракты, а не длинное архитектурное эссе.
- `Acceptance Criteria` должны быть проверяемыми и привязанными к FR или ключевым сценариям.
- `Architecture & Contracts` должен быть главным местом для описания boundaries, runtime flow, source of truth, handoff-ов, ownership и docs topology.
- `Technical Considerations` и `Database Changes` не должны повторно объяснять архитектуру целыми абзацами; только специфичные решения своего слоя.

Если структура нарушена — исправить ещё на Step 2, не откладывая до Step 11.

### 3d. Guard Rails — Diagrams — правила генерации

Секция `## Diagrams` создаётся **всегда** для `integration` и `architecture`; для `backend` — если есть внешние зависимости или нетривиальный поток данных; для `UI-only` — не создавать.

Все диаграммы — **Mermaid** (```mermaid ... ```). Вставляются прямо в `prd.md` в секции `## Diagrams`.

#### Обязательный набор по типу фичи

| Feature Type | Диаграмма | Формат |
|---|---|---|
| integration | **Data Flow (sequence)** — кто инициирует, порядок вызовов, retry/fallback | sequenceDiagram |
| integration | **Component Overview** — границы сервисов, очереди, направления зависимостей | graph LR |
| integration | **Field Mapping** — маппинг полей между системами (если ≥5 полей) | таблица Markdown |
| backend | **Data Flow** — поток данных через сервис, где есть внешние вызовы | sequenceDiagram |
| architecture | **Component Overview** — новые компоненты, зависимости, границы | graph LR |
| architecture | **Deployment/Infrastructure** — если меняется инфра | graph TD |

#### Guard Rails для диаграмм

- Диаграмма должна покрывать **happy path + основной error path** (не только успешный сценарий).
- Участники sequence diagram — реальные компоненты из `codebase-analysis.md`, а не абстракции.
- В `graph LR/TD` — стрелки подписаны (протокол/событие), не просто `A --> B`.
- Field Mapping таблица: три колонки — `Source Field`, `Target Field`, `Transform` (пустая если нет трансформации).
- Если диаграмму невозможно построить из-за неизвестных данных — создать OQ: «Диаграмма X требует уточнения [чего]. Владелец: [роль]. Дедлайн: [дата/milestone].»

#### Placeholder при нехватке данных

Если данных для диаграммы недостаточно (Step 4 ещё не завершён или нет ответов из Step 5) — создать секцию с комментарием:

```markdown
## Diagrams

> ⚠️ Диаграммы будут добавлены в Step 10 после получения технических решений.
```

Агент возвращается к диаграммам в **Step 10** и заменяет placeholder готовыми диаграммами через StrReplace.

### 3c. Guard Rails — Functional Requirements

Перед записью каждого FR в prd.md проверь:

- ☐ Нет слова **«или»** при описании идентификаторов, полей, форматов — выбери один вариант явно
- ☐ Нет слов **«разумный»**, **«подходящий»**, **«настраиваемый»** без указания диапазона значений или дефолта
- ☐ Каждый FR, описывающий внешний вызов (API, webhook, интеграция), имеет **пару** с поведением при ошибке: `FR-X-err` или явный текст «при ошибке — ...»
- ☐ Формулировка однозначна для junior developer — нет двусмысленных слов

Если FR нарушает любой пункт — уточнить перед записью.

### 4. Completeness
Покажи Completeness block:
- Dimension: PRD draft
- 50% — Goals, Scope
- 75% — + User Stories, AC
- 100% — + Non-Goals, Success Metrics

### 5. User Stories — обязательные сценарии

При формировании User Stories убедиться, что среди них есть:
- Минимум **один negative story**: «Как оператор, если операция не выполнена — я хочу видеть понятное сообщение об ошибке»
- Для интеграционных фич: story про **повторную попытку** или ручной fallback

### 6. Transition Prompt
«Готов формировать финальный PRD? Напишите «да» или «готово» для перехода к Step 3 (путь проекта), либо уточните ответы.»

Перед переходом показать мини-чеклист пользователю:
- ☐ Все Goals — про поведение системы (не про переговоры)
- ☐ Все FR — без «или» и «разумный» без диапазона
- ☐ Есть минимум один negative User Story
