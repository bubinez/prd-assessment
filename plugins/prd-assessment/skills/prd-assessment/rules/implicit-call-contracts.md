# Implicit Call Contracts

**Implicit Call Contract** — соглашение: при определённом условии конкретный вызов должен быть сделан **явно**. Нарушение не обнаруживается типами или статическим анализом — только в рантайме или интеграционным тестом.

Если `codebase-analysis.md` содержит секцию `## Implicit Call Contracts` — она обязательна к прочтению перед реализацией и ревью.

## Worker — при реализации

Для каждой ветки, затрагивающей паттерн из `## Implicit Call Contracts`:

1. Найти соответствующую строку таблицы (ветка → обязательный вызов → нужен?)
2. Если «✅ нужен» — убедиться, что вызов присутствует **явно до `return`**, а не подразумевается через return value
3. Если ветка добавляется новая — добавить строку в таблицу в codebase-analysis.md

**Запрещено** считать задачу реализованной, если:
- Возвращается правильный статус/результат, но обязательный вызов (finalize, save, send_notification и т.п.) отсутствует
- Вызов присутствует «по аналогии» (скопирован из другой ветки), но таблица не проверена

## Reviewer — при code review

Для каждого изменённого метода/функции, затрагивающего паттерн из `## Implicit Call Contracts`:

1. Прочитать таблицу контракта для этого паттерна
2. Для каждой ветки с `✅ нужен` — найти явный вызов в коде. Отсутствие = **блокер для approve**
3. Проверить, что вызов стоит **до `return`** (а не после, и не только в одной ветке из нескольких)
4. Если добавлена новая ветка — проверить, что таблица обновлена

## Типичные паттерны (не исчерпывающий список)

| Паттерн | Обязательный вызов | Что теряется при пропуске |
|---------|-------------------|--------------------------|
| Celery конвейер с финализацией | `finalize_classification(id, result)` до `return` | DB-записи не создаются, статус не обновляется |
| Django ORM — изменение записи | `.save()` вместо `.objects.update()` | `post_save` сигналы не срабатывают |
| Django транзакция | явный выход из `atomic()` / `commit()` | данные не сохранены при исключении |
| Notification pipeline | `send_notification()` в success-ветке | пользователь не получает уведомление |
| Аудит / traceback | `update_traceback()` в каждой ветке | трассировка пропадает для конкретного пути |
| Cache invalidation | `cache.delete(key)` после записи в БД | кэш устарел, клиент читает старые данные |

## Сигналы опасности в коде

- «По образцу существующих задач» — без явной сверки с таблицей контрактов
- «Аналогично другим классификаторам» — без проверки, что обязательный вызов скопирован
- Новая ветка `if/else` в функции с известным контрактом — без добавления вызова в эту ветку
- AC в PRD описывает только `return value` («возвращает статус ML_CLASSIFIED»), не side-effect
